# AGENTS.md — Portfolio React

Personal SPA portfolio (Alejandro Fernández Polo) → `alejandrofernandezpolo.com`. React 18 + Vite 6, plain CSS, i18next EN/ES, EmailJS contact form. No router, no TypeScript, no linter, no CI workflows. Tests **do** exist (vitest, in `test/`). A separate vanilla-JS sub-app lives in `public/ugr/` (served at `/ugr`) — different stack, see below.

## Commands

```bash
npm run dev        # Vite dev server (HMR)
npm run build      # Production build → dist/
npm run preview    # Serves dist/ (also runs the /ugr middleware)
npm run preview:stop # Mata cualquier `vite preview` colgado (4173/4174)
npm test           # vitest run — 70 files, 879 tests, in test/
npm run test:watch # vitest in watch mode
```

**Verification gate = `npm run build` + `npm test`**; run both after every change. There is **no** lint/typecheck command. Do not add tooling (ESLint, Prettier, TS, another test runner) or new npm dependencies without asking. `@playwright/cli` is in devDependencies for one-off browser checks — there is **no** e2e suite.

**No commits without the author's explicit approval.** Never run `git commit` (nor `--amend`) unless the author has asked for the commit in that same turn: leave the change in the working tree, report it and **offer** the commit. A green gate is not approval.

## Architecture (React app)

- Entry: `index.html` → `src/main.jsx` (StrictMode) → `src/App.jsx`.
- `index.html` has an inline script setting `data-theme` from localStorage before React boots — keep it, it prevents theme FOUC.
- Eager: `Navigation`, `Hero`. Lazy via `Suspense`, in `lazy()` order: `Experience`, `Skills`, `Projects`, `Contact`, `Footer` (page order is Hero → Projects → Skills → Experience → Contact → Footer). Education is not a section — `Experience` renders it as a nested `<aside id="education">`.
- Theme: `data-theme` on `<html>`, localStorage key `theme`, default `'light'`. Light vars on `:root`, dark on `[data-theme="dark"]` in `src/index.css`.
- Toasts: **Sonner** (`sonner` dep). `<Toaster>` is mounted in `App.jsx` with `theme` bound to the app state; the neo-brutalist overrides live in `src/index.css` and need the `html` prefix to beat the variables Sonner defines on `[data-sonner-toaster][data-sonner-theme=…]` and injects at runtime.
- Data lives in `src/constants/{education,experience,projects,skills}.js` plus `social.jsx` (`LINKEDIN_URL`, `GITHUB_URL`, `socialLinks` with JSX icons). There is **no** `src/constants/index.js` and **no** `src/assets/icons/`. Image barrel: `src/assets/images/index.js` — always import images through it, never deep relative paths.
- Metadata lives in the static `<head>` of `index.html` (title, description, Open Graph, canonical, `Person` JSON-LD, favicon, font preloads). **Crawlers do not run JS**, so anything social/SEO must stay there, and the head is deliberately written in **English** (decided; Google will show English titles to Spanish searchers). Note that asset URLs in JSON-LD must point at `public/` (stable), never at `src/assets/` (hashed per build).
- `vite.config.js` has a custom `ugrStatic` middleware that serves `public/ugr/` at `/ugr` in dev **and** preview. **Do not edit `vite.config.js` without explicit approval.**

## `/ugr` sub-app (separate stack)

- Vanilla JS, no build step, no framework. `public/ugr/index.html` loads plain `<script>` tags in fixed order (`data.js` → `docentes.js` → `app.js`, then `src/bootstrap.js` as a module) that communicate through globals — order matters, and `app.js` is an IIFE monolith (~2.3k lines: estado y cableado).
- **Convalidaciones dentro de Progreso (I-12, 2026-10-16).** No hay pestaña ni «motor de propuestas»: las convalidaciones son **una sola lista** en `progress.equivalences` — `{ id, origenes: [{codigo, nombre}], destinos: [codigoUgr], creditos, calificacion, estado }`, con `estado` ∈ pendiente/aprobada/rechazada— y la **sección vive dentro de la vista de Progreso**, plegada tras su botón (`src/ui/progress-dashboard.js`; `src/progress/convalidaciones.js` son las reglas puras). La asignatura de destino **no se marca a mano**: se **calcula** (`destinosAprobados`), de modo que aprobar una convalidación la da por superada y borrarla la devuelve a sin estado; «convalidada» no está en el desplegable de estados. El vocabulario viejo (`solicitada`/`concedida`/`denegada`) se traduce al leerlo. Los **suspensos** son un contador por asignatura (`progress.fails`), informativo y sin efecto en los ECTS. La antigua sección «Equivalencias UNED / Grado Superior → UGR» **se retiró entera**, y con ella el formato viejo de `equivalences`: al normalizar se cae, así que nadie ve convalidaciones que no sean suyas.
- **La sección de convalidaciones, por dentro (2026-10-16).** El alta va **por listas y de N a N**: el origen es texto libre y entra con «Añadir» (o Enter en el campo); el destino se elige del catálogo —el desplegable lleva delante «Elige una asignatura…» y **«Créditos libres»**— y también se añade. Cada lista es de chips con su botón de quitar, sin repetidos por código, y el envío exige **≥1 origen y ≥1 destino**. El borrador vive en el módulo, no en el DOM, porque el dashboard repinta la sección entera. Los **créditos se suman solos** de las asignaturas elegidas y el campo va `readonly`; **«Créditos libres»** (`DESTINO_LIBRE`, código reservado `LIBRES` en `src/progress/convalidaciones.js`) **no es una asignatura** —no tiene ECTS, no da ninguna por superada y no se pinta como «fuera del catálogo»— y, con él en la lista, el campo **pasa a editable** y lo que se escriba se suma **encima** de lo que dan las asignaturas.
- **Docentes: dos capas desde I-15 (2026-10-15).** El modelo es el del volcado de la hoja de la ETSIIT: **asignaciones** (`DOCENTES` en `public/ugr/docentes.js` y `docents` del dataset) = qué profesor da la teoría de una letra de grupo o las prácticas de un subgrupo, y **perfiles** (`PROFESORES` en el mismo fichero y `profesores` del dataset) = uno por `(asignatura, modalidad, nombre)` con dificultad, opinión, `cruzada` y comentarios **sin autor**. La dificultad de la asignatura va por modalidad (`{teoria, practicas}`) en la propia asignatura. Las siembra `tools/ugr-pipeline/emit-seed.mjs` — no las edites a mano.
- **Receta de los datos oficiales (repetible cada curso).** Dos documentos de la ETSIIT, los dos del curso en vigor, y ninguno se edita a mano: **(1) guías docentes** — `https://etsiit.ugr.es/informacion-academica/grados/graduadoa-ingenieria-informatica` lista las 96 asignaturas del Grado y cada guía trae «Profesorado» (teoría por letra de grupo, prácticas por número) → `node tools/ugr-pipeline/scrape-guias.mjs` escribe `tools/ugr-pipeline/guias-docentes.json`; **(2) horarios** — `https://etsiit.ugr.es/docencia/grados/horarios` → «Horarios GII (26-27).pdf», una página por grupo de teoría con cada subgrupo de prácticas en su franja → `node tools/ugr-pipeline/scrape-horarios.mjs` escribe `tools/ugr-pipeline/horarios-grupos.json` (por cada letra de grupo, su teoría y sus subgrupos de prácticas con sus franjas). **(3)** `node tools/ugr-pipeline/refresh-horarios.mjs` **reconstruye** el horario de `public/ugr/data.js` con ese fichero: repasa teoría y prácticas de las asignaturas que ya están (añade, corrige y quita), **incorpora las del plan que el horario publica** —las optativas de cuarto— y deja intactas las que no publica (el TFG, las prácticas de empresa). **(4)** `emit-seed.mjs` (muestra) y `extract-private-master.mjs` (maestro) cruzan los dos documentos con el catálogo, y el autor regenera el paquete con `build-package.mjs`. Al cambiar de curso solo hay que mirar la URL del PDF y el nombre de la titulación; `npm test` cruza los dos documentos asignatura a asignatura y avisa si alguno cambia de forma.
- **La UGR como tercera fuente, y quién manda (decisión del autor, 2026-10-16).** Las guías de la ETSIIT de las asignaturas de mención («(Especialidad …)») **no publican profesorado**; las páginas de asignatura de la UGR sí. `node tools/ugr-pipeline/scrape-ugr-asignaturas.mjs` las vuelca a `tools/ugr-pipeline/ugr-asignaturas.json`, y `guias.js` (`guiasConRelleno`) **rellena solo lo que falta** —teoría o prácticas por separado—: donde la UGR **contradice** a la ETSIIT, **mandan los datos de la ETSIIT** y no se pisa nada. El cotejo de las 96 asignaturas, fila a fila y ya resuelto por esa regla, lo regenera el propio scraper en `planes/discrepancias-ugr.md` (hoy: 63 diferencias, **2 contradicciones reales**); las letras y los subgrupos se comparan contra **lo que tiene la app** (`data.js`, del horario), no contra la guía.
- **Las asignaciones salen de las guías docentes, no del volcado.** La hoja dice qué profesor da cada `(asignatura, modalidad)` pero no las letras de grupo; quien lo publica es la ETSIIT, en la sección «Profesorado» de cada guía (teoría por letra de grupo, prácticas por **número** de grupo). `guias.js` cruza la guía con el catálogo y con los subgrupos del horario: el número de prácticas es la **posición** en esa lista (`1` es el primero), y el reparto por letra **no es uniforme** (IG: A3 B3 C2 D2 E2), así que no hay regla que lo reconstruya. Una asignación cuyo destino no exista en `data.js` **no se emite** (se cuenta y se informa): el horario es quien manda sobre qué subgrupos hay.
- **`data.js` es el horario del Grado, no solo de los cuatro cursos obligatorios.** Desde el repaso con los horarios oficiales tiene **93 asignaturas** (10 de 1º, 10 de 2º, 30 de 3º y 43 de 4º), incluidas las optativas de mención, cada una con sus grupos, su teoría y sus prácticas; el plan de la muestra cubre esas 93 y deja **una** fila en «solo plan» (el segundo `RI`, Robótica Industrial: el plan trae dos asignaturas con el mismo código y el horario no las distingue). Lo genera `refresh-horarios.mjs`: no se edita a mano.
- **El progreso se cuenta en créditos, con las cifras de la UGR.** En «Progreso» no hay asignaturas «pendientes»: sin estado propio están **sin marcar** (`marked` en el modelo, opción «Sin marcar», y el estado vacío borra la marca en el reducer). Lo que está pendiente son los **créditos**, y se miden contra el título: **60 básicas + 90 obligatorias + 48 de una mención + 30 optativas + 12 del TFG = 240** (lo verifiqué en `grados.ugr.es/informatica/docencia/plan-estudios`). Las **barras por curso** usan los 60 ECTS de cada curso del plan, no la suma del catálogo —que trae las optativas de las cinco menciones y nadie cursa las cinco—, y el **«ECTS pendientes»** del resumen es lo que falta para los 240. La **mención elegida** se guarda en el estado (`progress.mencion`, vacío = sin decidir). Ojo con las dos reglas, que son distintas: el plan pide **48 ECTS de materias de mención** (que se pueden cubrir con asignaturas de cualquier mención) y el título lleva **una** mención (se solicita y la Escuela asigna una, `etsiit.ugr.es/docencia/grados/eleccion-mencion`), que se obtiene cursando **todas** las materias de su módulo de especialidad; las que se eligen son las **30 optativas** (complementos de la mención, prácticas o módulos de otras titulaciones). Fuente: `grados.ugr.es/informatica/informacion/organizacion`. Las asignaturas del **plan sin horario** (TFG, prácticas y la `RI`) cuentan y se marcan igual: para eso el plan lleva `creditos`. El **resumen de cómo se consigue** solo se enseña con el catálogo del volcado, es decir, con la contraseña. La **guía completa** del título (los 240, las cinco menciones con sus 8 materias, las vías de la optatividad, el B1 y lo que queda por verificar) está en `planes/guia-oficial-grado.md`, comprobada contra el catálogo.
- **Un solo filtro de mención, en las dos listas.** `filterSubjectsByMention` (`plan.js`) es la regla de los dos desplegables —el de la lista de datos (`subjects-mencion`) y el de la tabla del progreso (`progress-subjects-mencion`, bajo «Proyección del plan»)—: elegir una mención oculta **solo** las asignaturas de las otras, nunca las que no tienen mención (el núcleo común). En la tabla del progreso, además, los ECTS de los separadores de curso se calculan sobre **todas** las asignaturas del curso, no solo las visibles.
- **Cabecera pegajosa en las tablas largas** (`src/ui/sticky-headers.js`, cargado en `bootstrap.js`): mide cada tabla y, si pasa de **vez y media** la ventana, marca su contenedor —`is-tall` le quita el `overflow-x` para que la cabecera se pegue a la ventana, `is-tall-scroll` (cuando la tabla no cabe a lo ancho) le pone tope de alto y la cabecera se pega dentro—. Un contenedor con `overflow` anula el sticky contra la ventana: es justo el fallo que tenía la regla anterior, que se aplicaba sin medir y no pegaba nada.
- **El paquete cifrado y la contraseña (I-11, rebanada 3).** El panel «Catálogo» tiene el campo de contraseña y el botón **Desbloquear**: `src/package/unlockPackage.js` descarga `package.enc.json`, lo descifra con `crypto.js` y lo valida; `app.js` avisa, ofrece copia y lo importa como catálogo **propio** con el id `…+volcado` (distinto al de la muestra, para poder volver a ella desde «Catálogo activo»). La contraseña **no se guarda** en ningún sitio, y `catalog-remote.js` no toca un catálogo importado (no viene del manifest). ⚠️ **La contraseña de prueba es `1234`: hay que cambiarla antes de producción**, y el artefacto generado con ella **no se commitea** (con una contraseña conocida el volcado deja de estar cifrado de verdad).
- **Qué es muestra y qué es privado (decisión del autor, ajustada el 2026-10-22).** La **muestra** sin contraseña son las **asignaciones reales** de las guías (nombres y grupos: los publica la ETSIIT), el **plan** —carácter y mención de cada asignatura, las menciones con su nombre largo y las asignaturas del plan sin horario— y los **perfiles** del fixture `tools/ugr-pipeline/sample-docents.json` (sus dificultades). Las **opiniones** de esos perfiles son **inventadas**: `tools/ugr-pipeline/sample-opinions.js` las deriva de `(asignatura, modalidad, nombre)` con un hash (estables e idempotentes) y `fictionalize-sample.mjs` reescribe el fixture; el catálogo sale con `meta.sampleOpinions: true` y la **ficha del profesor avisa** de que son de ejemplo. Por eso `test/ugr-tools/no-leak.test.js` ya no dispensa ninguna opinión: si aparece texto de la hoja en `public/`, es una fuga. Lo **privado** es el volcado completo (nombres, dificultades, opiniones y comentarios reales): `tools/ugr-pipeline/extract-private-master.mjs` lo convierte en `privado/catalogo.json` (ignorado por git) y `tools/ugr-pipeline/build-package.mjs` lo cifra en `public/ugr/datasets/ugr/gi/package.enc.json` (el autor lo ejecuta con su contraseña; nadie más la conoce). El historial de git y los dos `docentes_excel.*` locales conservan el texto plano antiguo por decisión expresa: no se reescribe la historia. `test/ugr-tools/no-leak.test.js` vigila que lo **exclusivo** del volcado no vuelva a los ficheros versionados.
- **Dos mundos: datos de muestra y datos personales (2026-10-22).** El store guarda **un documento `userState` por mundo** —claves `"sample"` y `"current"`— y las filas que cuelgan del usuario llevan `scope`: `configs` (que viven en las ranuras de `localStorage`, no en la tabla `configs`) y las valoraciones propias, que desde el esquema **v3** están en **`ownReviews`** con clave `scope|docentKey` (la tabla `reviews` queda declarada y vacía porque Dexie no deja cambiar la clave primaria de una tabla). ## i18n (easy to get wrong)

- Exactly 8 namespaces: `hero`, `experience`, `contact`, `projects`, `navbar`, `education`, `skills`, `footer` — **no `certifications` namespace**.
- New namespace requires **three edits** in `src/libs/i18n/i18n.js` (import both langs, add to `resources`, add to `ns` array) **plus** JSON files in **both** `src/locales/en/` and `src/locales/es/`.
- Pattern: constants hold non-translatable data + an `id`; components fetch text with `t("namespace.id", { returnObjects: true })` (see `Experience.jsx`, `Skills.jsx`, `Projects.jsx`, `Education.jsx`).
- Date ranges are **inline** in constants as `date: { en: "...", es: "..." }`, rendered via `exp.date[lang]`. Locale JSONs contain no dates — keep them inline.
- All user-facing UI text must go through `t()` in both languages.
- `useLang()` (`src/hooks/useLang.js`) returns the base code (`en`/`es`, normalized with `split("-")[0]`) and re-renders on `languageChanged` (with cleanup). `App.jsx` uses it for `<html lang>`; mirror that pattern for live language updates.
- Detection order: navigator → htmlTag → cookie → localStorage; preference cached. Fallback `en`, `defaultNS: "hero"`.

## Styling

- One CSS file per component: `src/components/css/ComponentName.css`, imported as `import "./css/ComponentName.css"`.
- **Never remove/rename existing CSS custom properties** in `src/index.css` — themes break silently. New vars go in both `:root` and `[data-theme="dark"]`.
- Visual language is **neo-brutalist**: thick borders (`3px solid var(--ink)`), hard offset shadows (`box-shadow: 8px 8px 0 var(--shadow)`), display type, and coloured section bands via the `--band-*` tokens (in both themes). The old glassmorphism is gone — `--card-bg`, `--glass-border` and `--glass-shadow` no longer exist.
- Breakpoints: `900px` and `560px` are the main ones (every component sheet + `src/index.css`); there are also `1200px` in `src/index.css` and `995px` in `Hero.css`/`Navigation.css`. **There is no 480px breakpoint** (the old copilot-instructions claimed one).
- Fonts: `Anton` (display), `Archivo` (body) and `Space Mono` (mono) — declared with `@font-face` in `src/index.css`, files in `src/assets/fonts/`, preloaded in `index.html`. The legacy `Outfit` font and the `*-old` design tokens were removed with the redesign.
- Avoid new `!important` and layout inline styles. The `style={{ "--d": … }}` delays in `Hero.jsx` are animation timing, not layout — those stay.

## Repo rules

- **Plans locate code by symbol, never by line number.** Line numbers drift on the first edit and send the next session to the wrong place: `grep -n "functionName"` first. Same for absolute paths written into a plan — the project moved out of Google Drive and stale paths still surface.
- **No commits without the author's explicit approval** — leave every change in the working tree and ask first, gate green or not. Only the author commits (or says when to).
- Functional components only; `export default function Name()`; destructured props; 2-space indent; no class components.
- No `console.log` / `debugger` left behind.
- All new code must be commented following the `documentation-and-adrs` skill (see "Code comments" below).
- No state libraries (Redux/Zustand) — local `useState` only.
- Navigation smooth-scroll uses a fixed **80px** offset for the fixed header; active section tracked via scroll listener in `Navigation.jsx`.

## Style note

Formatting is inconsistent (semicolons and quote style vary by file). Match the file you are editing rather than imposing a global style.
